# DataMind Agent 产品定义

> 版本基线：0.39.0（2026-11）。本文只描述本产品自有的目标、能力与边界；
> 能力状态与证据位置全部指向仓库内的代码与契约文档，不引用任何仓库外材料。

## 1. 一句话定位

**DataMind Agent 把企业文档、业务库、图纸与核验记录放进同一个可解释的问答面：
每个答案都带来源、定位与执行过程，证据不足时明确拒答。**

它不解决"能不能聊起来"，而解决答案之后的三个问题：这条结论来自哪一页、哪一行；
系统实际执行了什么；文件换一版之后，这个结论还成不成立。

## 2. 目标用户与场景

### 2.1 谁在用

| 角色 | 关心什么 | 产品给什么 |
| --- | --- | --- |
| 业务提问者 | 制度怎么规定、这批数据是多少 | 带原文定位与数据行的回答，答不了就说答不了 |
| 数据分析/运营 | 口径是否被改过、数字怎么算出来 | Schema 召回、只读 SQL、AST 校验与执行轨迹 |
| 质量/工艺工程师 | 规范版本、实测值、冲突判决 | 单位与版本核对、双方原值保留、来源权威登记 |
| 知识维护者 | 结论能否沉淀、能否追溯修订 | Wiki 词条、不可变版本、证据与运行履历 |

### 2.2 四条主场景

1. **企业文档问答**：制度、报告、扫描件、Office 文档、公式页；混合检索 + 引用定位 + 证据不足拒答。
2. **业务库问数**：自然语言 → 只读 SQL；Schema Linking、列权限门禁、指标口径校验、受限修复与回放。
3. **跨源联合问答**：同一问题同时落到文档、业务库与工业记录；冲突保留双方值，权威由人登记而非模型猜测。
4. **Wiki 知识沉淀**：把一次问答的证据与轨迹整理成四类词条（业务实体 / 指标 / 规范 / 结论），
   关系图入口、正文深链、版本与来源追索。

## 3. 要解决的问题

### 3.1 现有做法的三个断点

- **检索类工具停在"相关片段"**：给出三段摘录，但不说明这段话在原文哪一页、属于哪个版本，
  也没法判断"没检索到"和"文档里没有"的区别。
- **BI / 问数工具停在"一张表"**：SQL 能跑通，但列权限、指标口径、时间范围是否被模型改过，
  界面上通常看不出来。
- **知识库停在"文档堆积"**：文档入库即结束，结论、冲突、修订和责任人没有落点，
  几个月后没人能解释某条结论是怎么来的。

### 3.2 产品的四个设计选择

1. **证据先行**：引用不是装饰，而是可校验的定位对象（页 / 块 / 表格单元格 / 图纸实体 / 数据行）。
2. **契约化的解析**：解析结果先过统一契约（块、定位、关系），不合格的结果不会被当成"解析成功"。
3. **只读与门禁**：问数侧只发只读查询，权限在 AST 与数据库角色两层生效。
4. **失败显式**：解析、检索、权限、版本任何一环出问题，返回稳定错误码与原因，不静默降级成"看起来成功"。

## 5. 差异化

### 5.1 与"文档问答工具"的差别

多数工具把引用做成一句话加个文件名。这里引用是**存储中的定位对象**：只有库里确有定位时才附上，
查询失败记错误码也不阻断回答，但绝不从页码反推区域。解析侧同理——扫描件、Office、DXF 都先落到
统一契约，才允许进入检索。

### 5.2 与"BI / 问数工具"的差别

问数不是"生成 SQL 就执行"：列权限按 AST 作用域判定（带 schema 的同名表不会被当成 CTE 跳过），
指标必须命中注册口径，参数与占位符按文本序映射，修复有次数与预算上限。
每次运行落 `runs` / `trace_events`，可以回放"它当时到底跑了什么"。

### 5.3 与"知识库 / Wiki"的差别

一般 Wiki 与问答是两套数据。这里 Wiki 是**问答证据的投影**：词条引用具体运行与证据，
来源换版后标"待重新核验"，历史版本不可变，冲突双方原值都保留。
自动生成的内容只进草稿，发布与事实核验分开记账。

### 5.4 结构性优势

- **同一套证据模型贯穿三种来源**：文档块、SQL 行、图纸实体都能落到证据节点上。
- **版本被当成一等公民**：文件版本、解析器版本、来源版本、规范版本、词条版本各自记账，
  不合并成"最新版"。
- **确定性优先**：能规则判定的不用模型；模型只出现在生成与理解环节，且版本可登记。

## 6. 质量与可信原则

以下六条不是口号，每条都能在代码里找到对应实现。

1. **可解释**：答案附带检索命中、引用定位、SQL 与执行轨迹；前端证据星图可点开来源。
   实现：`datamind/agent.py`、`datamind/evidence_graph.py`、`/v1/runs/*`。
2. **可回放**：运行、事件、证据与计划摘要持久化；V-CAR 支持断点恢复与只重跑受影响子图。
   实现：`datamind/vcar.py`、`db/migrations/019_evidence_graph.sql`。
3. **证据可追溯**：引用只附存储中确有的定位；PDF 定位查询同时读两套存储，
   不会对"有 11 条定位的文档"谎报 0 条。
   实现：`datamind/knowledge.py`、`tests/test_rag_locators.py`。
4. **失败如实暴露**：解析状态五态、`partial` 带原因、`worker.alive=false` 明说任务不会自行推进、
   0 切片文档被选中时返回 `DOCUMENT_SELECTION_NOT_SEARCHABLE` 而不是"无证据的成功答案"。
5. **不伪造身份与数值**：源文件没有句柄时用位置身份并显式声明缺口，绝不编造 handle；
   模型段测不到就写 `null` 并附原因，不用 mock 延迟或 0 冒充。
   实现：`ingestion/cad_dxf_v2.py`、`docs/PERFORMANCE.md` §6.3。
6. **权限闭包**：读接口与写接口执行同一套归属规则，越权表现为"不存在"；
   私有 PDF 的向量、快照、检索各自独立鉴权，不因换个入口就扩大可见范围。
   实现：`datamind/visibility.py`、`datamind/pdf_search.py`、`docs/SESSIONS.md` §4。

## 7. 边界与非目标

明确不做，避免把"没做"读成"做不好"：

- **不做通用 BI 平台**：不提供自助建模、报表编排、指标市场；只回答"这个问题能不能被证据支持"。
- **不做写入型业务系统**：问数链路只发只读查询，不承担下单、改价、回写。
- **不做通用 CAD**：不覆盖 DWG/DGN、三维装配、整批制造验收；DXF 之外需外部转换器。
- **不做全文审阅式比较**："选了 8 份文件"不等于"读完了 8 份文件"；
  多文件能力只承诺相关片段覆盖与逐文件引用。
- **不做模型裁决**：冲突不按相似度、排序分或模型置信度定权威；权威必须人工登记。
- **不做自动事实合并**：名称相近只产生合并建议，实体归并需要业务标识或人工确认。
- **不训练、不分发模型**：仓库不含任何权重，生成模型直连上游，嵌入与 OCR 权重按
  [权重清单](MODEL_WEIGHTS.md) 单独获取。
- **不承诺生产 SLA**：默认本机回环部署；跨机使用前必须按 [部署边界](DEPLOYMENT_BOUNDARIES.md)
  配置认证、代理、数据库角色与密钥。
- **不做隐藏推理记录**：只展示真实执行事件与输入输出摘要，不生成、不保存模型内部思维过程。

## 10. 维护规则

1. **能力状态变更必须同时改两处**：本文件 §4 与对应证据文件；只改一处视为未完成。
2. **新增数字必须可复现**：由仓库内脚本产出，并写进 [性能](PERFORMANCE.md) 或对应验证文档；
   不接受"估计""大约"的量化表述。
3. **新增能力先进矩阵**：状态为"未做/部分"的能力不得在其它文档里被描述为已完成。
4. **边界与能力同权重**：任何能力条目都必须写清"不覆盖什么"，没有边界的条目不予合入。
